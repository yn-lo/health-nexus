# 层边界规范

## 设计意图

**为什么采用双 MPA 而非单 SPA？**
患者门户与员工门户面向完全不同的用户群体，权限模型、UI 风格、功能集合均无交集。
双 MPA 使两个门户可以独立加载，患者端不会下载管理端的代码，减小首屏体积；
同时避免了单 SPA 中复杂的路由权限分叉和懒加载边界问题。

**为什么需要 shared 层？**
两个门户共享认证流程（统一登录页）、API 客户端、基础 UI 组件和类型定义。
将这些抽取到 shared 层消除重复代码，确保 API 契约和类型定义的一致性。

## 依赖方向

```
chat ──→ shared ←── staff
  │        ↑          │
  └──→ stores ←───────┘
```

- `chat` 和 `staff` 可以依赖 `shared` 和 `stores`
- `shared` 不得依赖 `chat` 或 `staff` 中的任何模块
- `chat` 和 `staff` 之间不得存在任何直接依赖
- `stores` 可以依赖 `shared`（如调用 shared/api），但不得依赖 `chat` 或 `staff`

## 各层职责

| 层 | 职责边界 |
|------|------|
| `shared/` | 可复用基础设施：API 封装、通用组件、类型、工具函数、布局、共享页面。不包含任何特定门户的业务逻辑 |
| `chat/` | 聊天门户：聊天对话、SSE 流式响应、科室浏览、健康文章、个人中心。面向所有已登录用户（不限角色） |
| `staff/` | 管理侧业务：文章审核、AI 供应商配置、安全规则、危机事件、审计日志。仅面向员工/管理员角色 |
| `stores/` | 全局状态：认证令牌与用户信息（auth.ts）、聊天会话与消息（chat.ts）。是跨组件状态的唯一归属地 |

## 具体规则

依赖方向与层隔离规则由架构治理测试强制执行，参见 `tests/arch/governance.test.ts`。
违反依赖方向的 import 将导致 CI 失败。
